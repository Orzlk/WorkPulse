# WorkPulse 项目、Git 记录与 AI 周报/月报设计

## 1. 文档状态

- 日期：2026-08-23
- 状态：需求设计基线，待用户审阅
- 适用项目：WorkPulse

## 2. 背景与目标

WorkPulse 需要从单纯的工作日志和任务看板，扩展为个人工作活动记录工具。用户可以随时记录工作进度、临时想法和待办事项；应用定期读取指定本地 Git 仓库的提交摘要；AI 根据用户确认的数据整理收件箱，并按自然周或自然月、按项目生成周期报告。

目标如下：

1. 记录动作足够轻量，不要求用户在输入时完成完整分类。
2. 工作日志、任务、Git 仓库和 Git 提交都能归属到项目。
3. Git 扫描只读本地仓库，不修改仓库内容。
4. AI 只分析用户授权的时间范围、项目和数据类型。
5. 周报和月报突出核心功能、缺陷修复、重构维护和后续工作，而不是逐条罗列提交。
6. 数据保存在本地 SQLite，并支持版本升级迁移和完整数据备份迁移。

## 3. 范围

### 3.1 本期包含

- 项目管理。
- 统一收件箱记录。
- 收件箱到工作日志或任务的 AI 整理建议。
- 本地 Git 仓库添加、校验、定期扫描和手动扫描。
- Git 提交摘要去重和历史查询。
- 自然月筛选。
- 自然周筛选（周一至周日）。
- 按项目生成 AI 周报和月报。
- 多仓库、多项目筛选。
- 数据库版本迁移、自动备份、完整导出和导入。

### 3.2 本期不包含

- GitHub、GitLab 等远程平台 API。
- Git hooks。
- 完整 diff、具体文件路径和源代码片段存储。
- 一条记录归属多个项目。
- 多用户协作和云端同步。
- 每次输入后立即调用 AI。
- AI 直接打开或读取 SQLite 数据库文件。

## 4. 核心概念

### 4.1 项目

项目是工作内容的主要归属维度。一个项目可以关联多个仓库；日志、任务和收件箱记录最多归属一个项目，也可以暂不归属项目。

项目支持名称、描述、颜色、启用/归档状态和创建更新时间。

### 4.2 收件箱记录

收件箱用于保存零散、临时、未整理的内容。创建记录时不要求用户决定它是日志还是任务。

每条收件箱记录保存：

- 原始内容。
- 创建时间和最后更新时间。
- 可选项目、仓库、任务和标签。
- 是否纳入月报。
- 整理状态：未整理、已确认、已忽略、已归档。
- AI 最近一次整理建议及确认时间。

原始内容不可被 AI 静默覆盖。

### 4.3 Git 仓库

仓库由用户手动添加本地路径，并指定所属项目。仓库可以启用或停用自动扫描。

仓库保存：

- 本地路径。
- 仓库名称。
- 所属项目。
- 启用状态。
- 扫描间隔。
- 最近扫描时间。
- 最近成功扫描的 commit。
- 最近一次错误信息。

仓库更换项目后，历史 Git 提交在报告查询时跟随仓库当前所属项目。

### 4.4 Git 提交记录

只保存提交级摘要：

- 仓库。
- commit hash。
- 提交时间。
- 作者。
- 扫描时仓库检出的当前分支。
- 提交信息。
- 修改文件数量。
- 新增行数。
- 删除行数。

同一仓库的同一 commit hash只能保存一次。

## 5. 工作流设计

### 5.1 快速记录

用户可以从工作日志页面、全局快捷键或托盘菜单快速输入内容。输入内容默认进入收件箱或直接成为工作日志，具体入口由界面提供明确选择。

推荐默认行为：

- 快速日志入口直接创建正式工作日志。
- 快速想法入口创建收件箱记录。
- 快速任务入口直接创建任务。

### 5.2 AI 整理收件箱

AI 整理采用“批量触发、建议确认”模式：

1. 用户点击“AI 整理收件箱”。
2. 用户选择要整理的记录，默认选中未整理记录。
3. 主进程读取这些记录并发送必要内容给配置的 AI 服务。
4. AI 返回类型、标题、摘要、项目、仓库、标签和是否纳入月报的建议。
5. 用户逐条或批量确认、修改或忽略。
6. 确认后才创建或更新正式日志、任务和关联关系。

生成月报前，如果存在未整理记录，应用只提醒用户，不自动调用 AI。用户可以继续生成，也可以先进入整理流程。

### 5.3 Git 扫描

首次添加仓库时导入最近 30 天的提交；后续扫描以最后扫描状态和 commit hash 为依据增量读取。

扫描触发方式：

- 应用启动后执行一次。
- 默认每 30 分钟执行一次，可在设置中调整或关闭。
- 用户可以手动立即扫描单个仓库或全部仓库。

扫描过程必须在主进程执行，使用只读 Git 命令或等价只读实现。仓库不存在、路径无效、权限不足或 Git 命令失败时，只更新仓库错误状态，不影响其他功能。

### 5.4 项目归属调整

- 仓库可以手动调整到其他项目。
- 任务、日志和收件箱记录可以手动修改项目。
- AI 可以提出项目建议，但不能绕过用户确认。
- 仓库调整项目后，历史提交按当前仓库项目参与月报。
- 删除或归档项目不会删除其日志、任务、仓库和 Git 记录；未重新归属的内容进入“未归属项目”。

### 5.5 月报生成

月报支持手动生成和自动提醒：

- 用户可以选择任意自然月手动生成。
- 每月首次启动时提醒生成上个月月报。
- 自动提醒不自动调用 AI。
- 生成时默认选择所有启用仓库和全部项目。
- 用户可以取消选择项目或仓库。

时间范围采用左闭右开规则。例如 2026 年 8 月查询：

```text
2026-08-01 00:00:00 <= record_time < 2026-09-01 00:00:00
```

月报默认数据源：

- 已确认的工作日志。
- 已确认的任务及其状态和完成时间。
- 选定自然月中的 Git 提交摘要。
- 用户明确标记纳入月报的收件箱记录。

月报不默认包含未确认的收件箱记录、完整 diff 或具体文件内容。

### 5.6 周报生成

周报与月报复用同一套数据来源和生成流程，区别是统计周期按自然周计算：

- 用户可以选择任意已结束的自然周手动生成周报，默认建议最近一个完整自然周。
- 自然周固定从周一开始，到下周一 00:00:00 结束，界面展示为周一至周日。
- 时间范围采用左闭右开区间 `[周一 00:00, 下周一 00:00)`，不使用“最近 7 天”替代自然周。
- 周报严格提取范围内的已确认工作日志、已确认任务、选定 Git 提交摘要和明确纳入报告的收件箱记录。
- 报告按项目分组，AI 重点提炼本周核心功能、缺陷修复、重要进展、阻塞/风险和待跟进事项。
- 首次启动时，如果上一完整自然周尚未生成周报，应用可以提示用户；提示不自动调用 AI。
- 周报生成后同样进入人工确认和编辑流程，支持重新生成并保留历史版本。

## 6. AI 月报内容

AI 需要以项目为一级分组，不逐条输出 commit。

报告建议包含：

1. 本月总体概览。
2. 各项目的核心功能和成果。
3. 各项目的缺陷修复。
4. 重构、维护和配置变更。
5. 进行中的任务和未完成事项。
6. 风险、阻塞项和下月建议。
7. 未归属项目的工作内容。

AI 根据提交信息、工作日志和任务上下文自动判断“功能、缺陷、重构、文档、其他”等类别。用户可以编辑月报并保存最终版本。

### 6.1 AI 周报内容

周报采用与月报一致的项目分组和证据边界，但内容聚焦短周期进展：

1. 本周总体概览。
2. 各项目的核心功能和重要进展。
3. 各项目的缺陷修复。
4. 重构、维护和配置变更。
5. 进行中的任务、阻塞项和下周待跟进事项。
6. 未归属项目的工作内容。

周报和月报统一抽象为报告实体，至少包含 `report_type`（`weekly`/`monthly`）、`period_start`、`period_end`、`workspace_id`、项目和仓库筛选范围、数据快照、AI 生成状态和用户编辑后的正文。报告查询必须使用报告类型和时间范围共同约束，避免周报与月报相互覆盖或误用统计周期。

## 7. 数据存储与迁移

### 7.1 本地数据库

所有核心数据保存在 SQLite 数据库中，数据库位于系统应用数据目录。主进程负责数据库访问，Renderer 只能通过受控 IPC 获取经过筛选的数据。

### 7.2 数据库版本迁移

采用数据库版本号或迁移表管理结构变化。应用启动时：

1. 检查数据库版本。
2. 执行缺失的顺序迁移。
3. 迁移前创建备份。
4. 迁移过程使用事务。
5. 迁移后执行完整性检查。

迁移失败时保留原数据库和错误信息，不能破坏原有数据。

### 7.3 数据备份与跨设备迁移

支持导出完整 WorkPulse 迁移包，至少包含：

- SQLite 数据库。
- 项目和仓库配置元数据。
- 数据库版本信息。

导入时需要：

- 显示数据概览。
- 自动执行必要迁移。
- 处理重复记录。
- 对失效的本地仓库路径提供重新绑定。
- 支持合并或覆盖模式。

WAL 模式下不能只复制主数据库文件作为可靠备份，应使用 SQLite backup API 或等价安全方案。

## 8. AI 数据边界与隐私

AI 不直接访问 SQLite。主进程根据用户选择的时间范围、项目、仓库和数据类型组装输入。

默认发送：

- 选定范围内的工作日志文本。
- 已确认任务的标题、描述和状态。
- Git 提交信息及统计摘要。
- 用户明确选择的收件箱内容。

默认不发送：

- 完整数据库。
- API Key。
- 完整 Git diff。
- 源代码文件内容。
- 未选择项目或月份的数据。

报告和 AI 整理结果保存回本地数据库。使用第三方模型服务时，界面和文档必须明确提示选定内容会发送到配置的服务商；后续可扩展 Ollama 等本地模型。

## 9. 验收标准

1. 添加有效仓库后可以保存路径、项目归属并手动扫描。
2. 首次扫描只导入最近 30 天提交，重复扫描不会产生重复记录。
3. 定时扫描失败时显示错误，但不阻塞日志和任务功能。
4. 用户可以将仓库、任务、日志和收件箱记录调整到项目或设为未归属。
5. 仓库调整项目后，其历史提交在月报中归入新项目。
6. AI 整理必须先产生建议，用户确认后才能创建正式日志或任务。
7. 月报严格按自然月筛选，不以最近 30 天替代。
8. 周报严格按周一至周日筛选，不以最近 7 天替代。
9. 月报和周报默认按项目分组，并支持筛选项目和仓库。
10. 月报和周报不会逐条展示全部提交，而是提炼核心功能、缺陷修复和维护工作。
11. 数据库升级、备份、导入和恢复都有自动化测试覆盖。
12. AI 请求失败、Git 扫描失败和数据库迁移失败都有明确错误提示和可恢复路径。

## 10. 界面与交互方案

### 10.1 设计方向

界面采用“现代、安静、内容优先”的桌面生产力工具风格。保留 WorkPulse 现有的纸张、森林绿、酒红和金色品牌元素，但降低装饰边框、阴影和重复动画的密度。

设计原则：

- 记录动作优先于装饰展示。
- 项目是日志、任务、仓库和月报之间的一级归属维度。
- AI 建议必须可见、可修改、可确认。
- 状态不能只依赖颜色表达。
- 所有交互控件支持键盘焦点和明确的无障碍名称。
- 使用语义化颜色和统一的 4/8px 间距体系。
- 保持现有系统字体栈，不依赖远程字体加载。

### 10.2 应用壳与导航

随着收件箱、项目、Git 和月报加入，主界面由顶部标签导航调整为可折叠左侧导航。导航包含：

- 收件箱。
- 今日活动。
- 项目。
- 任务看板。
- 月报。
- 设置。

顶部区域提供：

- 当前项目选择器。
- 全局搜索入口。
- 快速记录入口。
- Git 扫描状态或待处理提醒。

增加 `Ctrl/Cmd + K` 命令面板，支持新建日志、新建任务、添加收件箱记录、搜索、扫描仓库和生成月报。

### 10.3 收件箱界面

收件箱作为随手记录的默认工作区：

- 顶部使用紧凑的 48–56px 快速输入框。
- 输入时不强制要求选择项目或记录类型。
- 列表展示原始记录、时间、项目、标签和整理状态。
- 右侧详情抽屉展示 AI 整理建议、项目、仓库和转化操作。
- AI 整理采用批量触发，确认前不创建或修改正式日志和任务。

### 10.4 项目和活动界面

项目页展示项目概览、任务、日志、Git 提交和月报入口。活动流将工作日志和 Git 提交按时间统一展示，并支持按项目、仓库和时间筛选。

项目概览至少显示：

- 未完成任务数。
- 当前月日志数。
- 当前月提交数。
- 关联仓库数。
- 最近活动时间。

### 10.5 任务看板与响应式布局

桌面宽屏继续使用多列看板；窗口较窄时切换为单列或可控横向滚动，不能让固定三列和草稿侧栏挤压主要内容。

拖拽之外必须提供可访问替代操作：

- 键盘拖拽。
- “移动到……”菜单。
- 明确的完成任务按钮。

编辑、删除、设置截止日期等操作不能只依赖 hover；键盘聚焦时也必须显示或可操作。

### 10.6 周报与月报界面

报告页顶部提供固定筛选栏：

- 报告类型切换：周报/月报。
- 周报使用自然周选择器，明确显示周一至周日；月报使用自然月选择器。
- 项目多选。
- 仓库多选。
- 未整理收件箱提醒。
- 生成、重新生成和保存按钮。

报告内容按项目分组展示。周报包含整体概览、核心功能、缺陷修复、重构维护、进行中事项、阻塞项和下周待跟进事项；月报增加下月建议。生成过程展示读取数据、分析提交、项目归类和生成报告等阶段状态。

## 11. 性能与体验要求

### 11.1 首屏和后台任务

- 首屏只加载当前页面和必要数据，不等待 Git 扫描或 AI 请求。
- Git 扫描在主进程后台执行，不能阻塞 Renderer 和用户输入。
- AI 整理和月报生成期间，界面保持可操作，并显示取消或失败状态。
- 页面按功能进行动态加载，避免所有页面代码在首屏一次性加载。

### 11.2 列表与查询

- 日志和活动流使用分页或游标查询。
- 数据量较大时使用虚拟列表，避免一次渲染全部记录。
- 搜索使用 250–300ms 防抖，并丢弃过期搜索结果。
- 任务和日志状态更新只刷新受影响的列表项，不触发整页无差别重渲染。
- React 组件只在有实际渲染成本并经过测量后使用 memo 化。

### 11.3 动效和视觉性能

- 动效优先使用 `transform` 和 `opacity`。
- 页面切换和反馈动效控制在约 150–300ms。
- 列表动画只应用于新增、完成和删除项，数据刷新时不重复播放全部动画。
- 避免大面积模糊、持续阴影动画和复杂背景特效。
- 支持 `prefers-reduced-motion`，减少动画时直接呈现最终状态。

### 11.4 视觉一致性和可访问性

- 统一图标尺寸、描边宽度、按钮高度和圆角。
- 正文保持可读字号，普通文本对比度达到 4.5:1。
- 浅色和深色主题分别检查文字、边框、焦点和禁用状态。
- 图标按钮必须有 `aria-label`，装饰性图标标记为隐藏。
- 看板拖拽、弹窗、抽屉和命令面板必须支持键盘焦点管理。

### 11.5 UI 验收标准

1. 用户打开应用后无需等待 Git 扫描或 AI，即可开始输入记录。
2. 收件箱、项目、任务、活动和月报之间可以通过主导航快速切换。
3. 主要功能在 400px 最小窗口宽度下仍可用，不出现不可控的水平溢出。
4. 日志、Git 活动和月报筛选不会触发全量数据加载。
5. 大量日志和活动记录滚动时不会因一次性渲染造成明显卡顿。
6. 所有核心操作都有加载、成功、失败和可恢复状态。
7. 键盘用户可以完成记录、搜索、项目筛选、任务移动和月报生成。

## 12. 标签与检索方案

### 12.1 标签定位

标签是轻量级的上下文分类，项目是正式的业务归属。两者不能互相替代：

- 项目回答“这条内容属于哪个工作项目”。
- 标签回答“这条内容具有什么主题、状态或属性”。

示例：

```text
项目：WorkPulse 重构
标签：#bug #前端 #待确认
```

### 12.2 多标签输入

日志、任务、收件箱记录和 Git 提交支持多个标签。用户可以在输入内容中直接使用 `#标签`：

```text
修复登录状态丢失问题 #bug #前端
完成月报页面初版 #功能 #项目管理
客户反馈需要增加导出功能 #需求 #待确认
```

输入规则：

- 一条记录可以包含多个标签。
- 标签通过空格或记录结尾识别。
- 原始内容必须保留。
- 标签单独保存，不再只依赖单个 category 字段。
- 输入时提供已有标签自动补全。
- 不存在的标签可以直接创建。
- 标签名称统一大小写和空白规则，避免产生重复变体。

### 12.3 简单层级标签

第一版支持使用 `/` 表达简单层级：

```text
#技术/前端
#技术/数据库
#状态/待确认
```

层级标签用于检索和浏览，不改变项目归属。搜索父级标签时默认包含其子级标签，例如搜索 `#技术` 可以匹配 `#技术/前端` 和 `#技术/数据库`。

第一版不实现复杂的拖拽排序、标签图谱或自动合并；后续可以增加标签重命名、合并和使用频率统计。

### 12.4 标签数据模型

建议新增：

- `tags`：标签名称、规范化名称、父标签、创建时间。
- `work_log_tags`：工作日志与标签的关联。
- `task_tags`：任务与标签的关联。
- `inbox_tags`：收件箱记录与标签的关联。
- `git_commit_tags`：Git 提交与标签的关联。

删除标签只删除关联关系，不删除原始记录。项目和标签都被删除或归档时，原始数据仍然保留。

### 12.5 全文搜索

全局搜索统一检索工作日志、任务、收件箱记录和 Git 提交摘要。搜索索引包含：

- 工作日志内容。
- 任务标题和描述。
- 收件箱原始内容。
- Git 提交信息。

使用 SQLite FTS5 或等价的本地全文索引，避免数据量增长后依赖全表 `LIKE` 查询。

搜索支持：

- 普通关键词：`登录`
- 标签搜索：`#bug`
- 多关键词组合：`登录 #bug`
- 标签排除：`#bug -#已解决`
- 项目筛选。
- 仓库筛选。
- 日期范围。
- 记录类型筛选：日志、任务、收件箱、Git。
- 未添加标签。
- 未归属项目。

多个普通关键词默认使用 AND 语义；短语搜索和更复杂的语法在实现时保持向后兼容。

### 12.6 标签浏览界面

标签浏览入口可以放在左侧导航或活动流筛选栏，提供：

- 最近使用标签。
- 标签树。
- 标签使用数量。
- 未分类快捷筛选。
- 标签包含和排除。
- 与项目、仓库、日期条件组合筛选。

搜索结果采用统一活动时间线，并明确标识来源：

```text
[工作日志] 修复登录状态丢失问题
[Git 提交] fix: refresh token expired handling
[任务] 增加登录异常提示
```

### 12.7 AI 与标签

AI 整理收件箱时可以建议标签，但必须用户确认。AI 还可以：

- 为未整理记录推荐已有标签。
- 发现可能重复的标签名称。
- 根据标签和内容辅助判断月报主题。

AI 不得静默重命名、删除或合并已有标签。

### 12.8 月报中的标签

月报仍以项目作为一级分组，标签作为辅助上下文：

```text
项目 A
  核心功能
  缺陷修复
  相关主题：前端、性能、待确认
```

用户可以在生成月报前按标签筛选数据，但标签不能替代项目分组。

### 12.9 标签与检索验收标准

1. 一条记录可以保存多个标签，并且原始内容不丢失。
2. 输入 `#技术/前端` 可以创建或匹配层级标签。
3. 搜索父级标签可以匹配其子级标签。
4. 搜索结果支持标签包含、排除、项目、仓库和日期组合筛选。
5. 可以快速找到所有未添加标签的记录。
6. 日志、任务、收件箱和 Git 提交可以在统一搜索中找到。
7. 搜索结果分页或虚拟滚动，不因全量渲染造成明显卡顿。
8. AI 标签建议在用户确认前不会修改正式数据。
9. 从旧版单分类字段迁移到多标签后，原有分类信息不丢失。

### 12.10 参考

本方案参考 flomo 的多级标签、包含/排除标签、无标签筛选、多关键词搜索和日期范围检索设计：

- https://help.flomoapp.com/basic/tag.html
- https://help.flomoapp.com/advance/search.html

## 13. 在线化兼容设计与三阶段路线

### 13.1 总体原则

WorkPulse 采用“本地优先、逐步在线化”的路线：

- 第一阶段保持单机可用，SQLite 是本地数据源。
- 第二阶段增加个人账号和云端同步，SQLite 仍作为离线缓存。
- 第三阶段增加团队空间、成员权限和共享项目。

Renderer 不直接依赖 SQLite。数据访问通过 Application Service 和 Repository 接口完成，当前使用本地 SQLite 实现，未来可以增加云端同步实现。

```text
Renderer
  ↓ IPC / Command
Application Service
  ↓
Repository 接口
  ├── Local SQLite（第一阶段）
  └── Cloud Sync / API（第二、三阶段）
```

### 13.2 第一阶段：本地优先单用户版

#### 阶段目标

完成核心记录、项目、标签、Git 扫描和 AI 月报功能，同时让数据模型具备未来同步条件。

#### 当前阶段包含

- 本地 SQLite 数据库。
- 默认个人工作空间。
- 项目、日志、任务、收件箱、标签和月报。
- 本地 Git 仓库路径管理和定期扫描。
- Git 提交摘要去重。
- AI 收件箱整理、自然周周报和自然月月报。
- 数据库版本迁移。
- 完整备份和跨设备导入导出。
- 左侧导航、项目筛选、统一搜索和多标签。

#### 现在必须提前完成的在线化基础

所有核心实体预留或采用以下字段：

- `public_id`：跨设备稳定 UUID。
- `workspace_id`：默认指向个人工作空间。
- `project_id`：可为空的项目归属。
- `created_by`、`updated_by`：当前指向本地用户身份。
- `created_at`、`updated_at`：统一保存 UTC 时间。
- `deleted_at`：软删除时间。

同时建立：

- `Repository` / `Service` 数据访问边界。
- `RepositoryBinding`，分离共享仓库身份和本地路径。
- `sync_operations` 本地操作队列。
- AI 任务状态和来源快照。
- 可重复执行的数据库迁移机制。

#### 第一阶段不包含

- 在线登录。
- 云端 API。
- 团队邀请和成员管理。
- 实时协作。
- 云端 Git 平台授权。

#### 进入第二阶段的条件

1. 本地核心数据模型稳定。
2. 迁移、备份和恢复测试通过。
3. 日志、任务、标签和项目的 UUID 稳定可用。
4. 所有主要写操作都经过 Application Service。
5. 本地操作可以被记录为可重放、可去重的同步操作。

### 13.3 第二阶段：单用户在线同步版

#### 阶段目标

让同一个用户可以在多台设备之间同步数据，同时保留离线使用能力。

#### 核心能力

- 用户注册、登录和设备管理。
- 云端个人空间。
- SQLite 本地离线缓存。
- 本地操作队列上传。
- 云端变更下载。
- 同步游标和断点续传。
- 云端备份和恢复。
- 仓库本地路径重新绑定。
- 多设备状态和最近同步时间。

#### 同步规则

- Git 提交以 `repository_id + commit_hash` 去重。
- 工作日志默认使用版本号和最后修改时间判断冲突。
- 任务使用字段级更新时间判断冲突。
- 删除通过 `deleted_at` 同步，不直接物理删除。
- 报告保存为版本记录，不覆盖其他设备的历史报告。
- 同步请求必须具备幂等操作 ID。

第一版不要求复杂 CRDT。日志追加、Git 提交不可变、报告版本化，任务和项目冲突提供明确提示即可。

#### 在线安全要求

- 全部 API 使用 HTTPS。
- 工作空间数据必须隔离。
- API Key 不进入同步数据。
- 用户可以控制哪些内容允许发送给 AI。
- 服务端保留审计日志和异常访问记录。
- 账号删除时提供完整数据导出。

#### 进入第三阶段的条件

1. 单用户多设备同步稳定。
2. 离线编辑和断网恢复可用。
3. 冲突提示和数据恢复流程明确。
4. 个人空间权限和数据隔离通过测试。
5. 云端备份、导出和删除流程可验证。

### 13.4 第三阶段：团队空间与多人协作版

#### 阶段目标

在个人空间之外提供团队空间，让多人围绕项目、任务、Git 活动和月报协作。

#### 核心能力

- 创建团队空间。
- 邀请和移除成员。
- Owner、Admin、Member、Viewer 角色。
- 项目成员和项目级权限。
- 个人记录与共享记录分离。
- 共享任务和看板。
- 共享 Git 仓库和提交摘要。
- 团队月报。
- 团队 AI 配置、调用额度和数据权限。
- 活动通知和变更历史。

#### 团队数据边界

- 个人空间内容默认不共享。
- 只有归属团队项目的日志、任务和 Git 记录进入团队空间。
- 团队月报只能读取当前用户有权限访问的项目。
- AI 生成团队报告前显示数据范围和可见成员。
- 仓库本地路径只属于具体设备绑定，不直接对团队公开。

#### 多人协作规则

- Git 提交是不可变活动，允许多个成员贡献到同一仓库。
- 任务状态和排序采用版本控制，冲突时保留用户修改并提示合并。
- 日志编辑保留修改者和修改时间。
- 月报采用版本历史，不允许无提示覆盖他人编辑。
- 项目和标签的删除默认采用归档，避免影响历史报告。

#### 第三阶段不强制包含

- 同一文本编辑器内的实时多人协同编辑。
- 完整 Git diff 在线浏览。
- 在线 IDE。
- 复杂组织架构和企业级审批流。

### 13.5 三阶段交付边界

| 阶段 | 主要目标 | 数据形态 | 用户形态 |
|---|---|---|---|
| 第一阶段 | 本地记录和 AI 月报 | SQLite 本地数据库 | 单用户、单设备为主 |
| 第二阶段 | 个人多设备同步 | SQLite 缓存 + 云端个人空间 | 单用户、多设备 |
| 第三阶段 | 团队项目协作 | 本地缓存 + 云端团队空间 | 多用户、共享项目 |

每个阶段都必须保持前一阶段的数据可迁移，不能通过重写数据库或丢弃本地数据实现升级。

### 13.6 在线化兼容验收标准

1. 第一阶段所有核心实体都有稳定的跨设备 ID。
2. 现有数据可以迁移到默认个人工作空间。
3. 时间字段可以在不丢失信息的情况下转换为 UTC。
4. 本地仓库路径和共享仓库身份分离。
5. 核心写操作可以生成幂等的本地操作记录。
6. 未来增加远程 Repository 实现时，不需要修改 Renderer 的业务交互。
7. 第二阶段可以在断网时继续记录，恢复网络后自动同步。
8. 第三阶段的个人空间和团队空间数据互相隔离。
9. 团队月报只使用当前用户有权限访问的数据。
